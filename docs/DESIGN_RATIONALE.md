# 设计思路

本文档记录 `DOCX Style Tree` 的关键设计思路。它服务于课程报告和答辩，重点说明项目如何从“写代码”上升到“做架构、做文档、做可复现的软件”。

## 问题定义

课程要求是根据给定 DOCX 文件自动提取主要结构信息，并按照预定义样式替换文档结构风格。

如果只把 DOCX 当成普通文本处理，很容易出现两个问题：

- 标题识别不稳定，例如正文里出现“第一章”“1.1”就可能被误判。
- 格式信息丢失，无法解释标题、正文和表格到底来自什么 Word 样式。

因此项目把问题定义为：

> 基于 OOXML 解析 DOCX 的结构和样式元数据，将 Word 文档转换为可解释的文档结构树，并提供样式规范化能力。

## 为什么选择 OOXML

DOCX 本质上是一个 ZIP 包，里面包含多个 XML 部件：

```text
word/document.xml
word/styles.xml
word/numbering.xml
word/header*.xml
word/footer*.xml
word/footnotes.xml
```

直接解析 OOXML 的好处：

- 可以在 Linux 服务端运行。
- 不依赖 Microsoft Word 或 LibreOffice。
- 可以解释标题来自哪种样式或 `outlineLvl`。
- 可以保留非目标部件，例如图片、脚注、批注和嵌入对象。
- 便于写自动化测试。

代价：

- 不能得到 Word 渲染后的精确视觉版面。
- 需要处理多种 OOXML 变体。
- 对没有规范使用样式的文档，不会强行猜测标题。

这个取舍符合课程题目，因为目标是结构提取和样式替换，不是完整的 Word 排版引擎。

## 为什么不使用正文文本匹配

早期思路可能会根据文本判断标题，例如：

```text
第一章
1.1
摘要
参考文献
```

这种方式简单，但不可靠。因为这些文本也可能出现在正文、题目、习题或目录中。

当前设计禁止正文文本匹配标题，改用：

- 段落自身 `w:outlineLvl`。
- 样式表中的 `outlineLvl`。
- 样式继承关系 `basedOn`。
- 样式 ID 和样式显示名称。

这样牺牲了一部分“猜测能力”，但换来了更高的可解释性和更低的误判风险。

## 为什么使用文档结构树

程序语言有 AST，Word 文档也可以抽象为结构树：

```text
Document
├── Heading 1
│   ├── Paragraph
│   ├── Table
│   └── Heading 2
└── Heading 1
```

这种抽象有三个好处：

- 便于 API 输出和前端展示。
- 便于比较模板与实际论文。
- 便于样式替换，因为可以按结构角色处理。

项目没有声称 DOCX 结构树等同于编译器 AST，而是借鉴 AST 的层级建模思想。

## 为什么保留 API、CLI 和报告脚本

三个入口服务不同场景：

| 入口 | 目的 |
|---|---|
| FastAPI | 对外集成，展示服务化能力。 |
| CLI | 本地批处理和调试。 |
| 报告脚本 | 生成课程演示素材。 |

它们都复用 `docx_style_tree` 核心包，而不是各自实现解析逻辑。这保证了测试、API 和演示结果一致。

## 开源软件方法体现

本项目结合“开源软件与技术”课程，采用了这些工程方法：

| 方法 | 项目体现 |
|---|---|
| 版本化接口 | `/api/v1/analyze`、`/api/v1/styles/apply`。 |
| 自动化质量检查 | `ruff`、`mypy`、`unittest`、`coverage`。 |
| CI | GitHub Actions 工作流。 |
| 许可证 | MIT License。 |
| 可复现测试 | 真实论文模板和外部 DOCX fixtures。 |
| 校验外部资源 | fixture manifest 保存 URL 和 SHA256。 |
| 文档体系 | README、架构文档、代码导读、路线图。 |
| API 文档 | FastAPI `/docs` 和 Doxygen。 |
| 路线图 | 规划 compare API、报告、示例和部署能力。 |
| 非目标声明 | 明确不做 PDF/OCR、查重、AI 写作。 |

这些内容比单纯增加代码量更重要，因为它们说明项目可维护、可复现、可继续协作。

## 架构决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| DOCX 处理方式 | 直接解析 OOXML | 部署简单，可解释性强。 |
| 标题识别 | 不用正文文本匹配 | 避免误判，符合结构解析目标。 |
| API 设计 | 使用 `/api/v1` | 保持未来兼容。 |
| 核心逻辑 | 放在 `docx_style_tree` 包 | API、CLI、报告都能复用。 |
| 报告输出 | 只显示结果 | 算法解释放文档，输出保持干净。 |
| 后续方向 | 模板一致性比较 | 与论文模板场景强相关，不超题。 |

## 当前系统边界

系统做：

- DOCX 结构提取。
- DOCX 样式替换。
- 结构树报告生成。
- API/CLI 调用。
- 复杂 DOCX 测试。

系统不做：

- PDF 或扫描件处理。
- 论文内容质量评价。
- 查重。
- 自动写作或润色。
- 完整 Word 排版预览。

明确边界可以让项目更可信，也更容易在课程报告中讲清楚。

## 后续演进思路

后续最自然的升级是模板一致性比较：

```text
template.docx -> Template Profile
paper.docx    -> Paper Profile
Template Profile + Paper Profile -> Compare Report
```

这一步会复用现有结构树、样式元数据和报告生成能力，而不是推倒重来。它能把项目从“解析工具”升级为“论文格式检查服务”，同时仍然严格围绕 DOCX 和样式结构。

## 总结

项目的核心价值不是某个复杂算法，而是把一个看似普通的 Word 文件处理任务拆解成：

- 稳定的 OOXML 解析核心。
- 清晰的 API 和 CLI。
- 可解释的结构树输出。
- 可复现的测试和 fixtures。
- 可展示的报告和文档。
- 有边界感的后续路线图。

这正是开源软件项目中比代码本身更重要的部分：架构、思路、文档和协作方式。
