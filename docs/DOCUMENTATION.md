# 文档体系

本文档说明项目文档如何组织，以及每类文档服务什么目标。对于“开源软件与技术”课程而言，文档不是附属品，而是项目能否被理解、复现、评价和继续维护的关键部分。

## 文档目标

文档体系需要回答四类问题：

| 问题 | 对应文档 |
|---|---|
| 这个项目是什么，怎么运行？ | `README.md` |
| 系统架构为什么这样设计？ | `docs/ARCHITECTURE.md` |
| 代码从哪里读，模块如何分工？ | `docs/CODE_GUIDE.md` |
| 后续可以如何迭代？ | `docs/ROADMAP.md` |
| 设计思路和开源方法是什么？ | `docs/DESIGN_RATIONALE.md` |
| API 细节如何查？ | FastAPI `/docs`、Doxygen |

## README 的职责

README 面向第一次打开仓库的人。它应该快速回答：

- 项目解决什么问题。
- 为什么它有价值。
- 如何安装和运行。
- API 如何调用。
- 示例结果长什么样。
- 到哪里查看更深入的架构和设计文档。

README 不应该承载所有解释，否则会变得冗长。因此架构分析、ATAM、代码导读和路线图都放在 `docs/` 目录。

## 架构文档的职责

`docs/ARCHITECTURE.md` 面向课程报告和答辩。它重点解释：

- 架构风格。
- C4 Context、Container、Component 图。
- 关键运行流程。
- 质量属性。
- 敏感点。
- ATAM 分析。
- 后续架构演进。

这份文档回答“架构设计到底好在哪里”。

## 代码导读的职责

`docs/CODE_GUIDE.md` 面向开发者和评审者。它重点解释：

- 代码阅读顺序。
- 模块职责。
- 核心公共 API。
- 文档树构建过程。
- 样式替换过程。
- 测试策略。
- 后续扩展点。

这份文档回答“代码是如何支撑架构的”。

## 设计思路文档的职责

`docs/DESIGN_RATIONALE.md` 面向课程报告。它重点解释：

- 为什么选择 OOXML 而不是 Word 自动化。
- 标题识别依据来自哪些 OOXML 结构和样式元数据。
- 为什么保留 API、React Demo、MCP、CLI、报告脚本多类入口。
- 如何体现开源软件课程的方法。
- 哪些事情明确不做。

这份文档回答“我们为什么这样做”。

## 路线图的职责

`docs/ROADMAP.md` 面向后续迭代。它重点解释：

- 如何把项目升级为论文格式一致性检查服务。
- `/api/v1/compare` 的设计方向。
- 后续报告、示例、批量检查和部署能力。
- 非目标范围。
- P0/P1/P2 优先级。

这份文档回答“这个项目还能怎么继续发展，但不超出题目范围”。

## 自动生成文档

项目支持 Doxygen：

```bash
make docs
```

输出：

```text
docs/api/html/index.html
```

Doxygen 适合查看函数、类和模块级注释；手写 Markdown 文档适合说明架构、设计决策和项目思路。两者作用不同，不应互相替代。

## 报告与截图

可视化报告通过以下命令生成：

```bash
make report
```

输出：

```text
outputs/extraction-report/
├── index.html
├── tree.svg
└── tree.json
```

报告页只展示解析结果，不包含算法解释。算法解释应留在 README、架构文档和课程报告中。

README 中使用的示例图保存在：

```text
docs/assets/frontend-demo-docxstruct.png
```

## 文档维护原则

- README 保持简洁，重点展示项目价值和快速上手。
- 深入解释放入 `docs/`。
- 新增功能时同步更新 README、代码导读和路线图。
- 新增 API 时同步更新 FastAPI 文档、README 示例和测试。
- 新增架构决策时在设计思路文档中记录原因和取舍。
- 输出报告不要夹带讲稿，保持结果视图干净。

## 面向课程的价值

在编程 Agent 能快速生成代码的背景下，项目价值不只在代码量，而在：

- 能否把问题拆成稳定的架构。
- 能否说明每个模块为什么存在。
- 能否通过文档让别人复现和继续开发。
- 能否用测试和 CI 证明结果可靠。
- 能否知道哪些功能不该做。

这也是本项目文档体系的核心目的。
